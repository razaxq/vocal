# ADR-0005：长输入的分段流水线与三层文本整理

- 状态：已采纳
- 日期：2026-09-14
- 取代：[ADR-0002](0002-text-injection.md) 中「会话结束后整段重转写」的部分

## 问题一：原设计对长输入是线性恶化的

第一版的定稿流程是：会话结束 → 把**本次全部音频**拼起来跑一遍 SenseVoice。

短句没问题，长输入就是灾难：说 3 分钟，松手后要重转写 3 分钟的音频，用户干等。
而且这段时间里屏幕上一个字都没有 —— 流式结果只在悬浮面板里显示，没上屏。

## 决策一：按句子边界切段，边说边定稿

```
主进程            持有音频缓冲，按 endpoint 切段
  ├─ stream 进程   OnlineRecognizer，只出实时文本和句子边界
  └─ finalize 进程 OfflineRecognizer + 标点 + 规则清洗
```

流式进程检测到 endpoint 时，回报「截至此刻消费了多少采样点」，主进程据此
从自己的缓冲里精确切出这一段交给定稿进程。音频只在主进程存一份。

两个工作进程**完全并行**：用户说第 N+1 段的时候，第 N 段已经在另一个核上定稿了。
长输入的定稿延迟因此被完全藏住，松手后只有最后一段需要真等（~200ms）。

副作用（是好事）：文字变成每隔几秒上一批屏，而不是憋到最后一次性吐出来。
用户全程能看见进度。

代价与对策：
- 音频缓冲会随时长增长 → `SessionAudioBuffer.compact()` 每 60s 回收一次已切走的部分
- 定稿可能翻车（SenseVoice 在极短片段上偶尔输出空串）→ 长度不足流式结果一半就回落到流式文本
- 段间顺序 → 定稿进程串行处理，天然保序

## 问题二：「整理成书面文字」到底要不要新模型

分三层，只有第三层需要新东西：

| 层 | 例子 | 靠什么 | 成本 |
|---|---|---|---|
| 语气词 / 口吃 / 重复 | 「嗯那个…我我我觉得」→「我觉得」 | **纯规则** | 微秒级，0 依赖 |
| 标点 + 数字格式化 | 「二零二六年三点五万」→「2026 年 3.5 万」 | 已有模型（CT-Transformer + SenseVoice 的 ITN） | 已在流水线里 |
| **书面化改写 / 合并碎句 / 分段** | 「这个吧，它那个性能不行，就是慢」→「该方案性能不足，响应偏慢」 | **必须 LLM** | 云端 API 或本地小模型 |

第三层 ASR 模型做不到 —— Paraformer 和 SenseVoice 是转写模型，你说「嗯」它就写「嗯」，
它们没有改写能力。

## 决策二：三层分开实现，各自可独立关闭

**第一层**：`src/shared/textCleanup.ts`，纯函数，在定稿进程里同步跑。

设计原则是**宁可漏删，不可错删**：
- 「这个方案不行」的「这个」是实词，必须保留
- 「这个，嗯，我觉得」的「这个」才是填充词
- 所以填充短语只在句首或被停顿标点包围时才删，孤立出现一律保留
- 叠词折叠阈值定在「出现 3 次」而不是 2 次，因为「刚刚」「看看」「谢谢」都合法
- 热词表自动纳入保护词，专有名词不会被误删

有回归测试（`npm test`），反例比正例更重要。

**第三层**：`LlmService.consolidate()`，OpenAI 兼容端点，两种时机：
- `onFinish`（默认）：会话结束后整理一次，退格替换已上屏文本
- `rolling`：每积累 300 字整理一次，只替换那一块

替换是危险动作，三道闸：
1. 目标窗口必须还是当初那个（`hwnd` 一致），否则拒绝退格
2. 退格数超过 `maxReplaceChars`（默认 1500）就拒绝
3. LLM 输出长度偏离输入 0.4~2.5 倍之外就认定跑题，丢弃

第三道闸是必须的：模型偶尔会「回答」而不是「整理」——
你口述「帮我看看这段代码」，它真的开始讲代码。

**任何一层失败都不影响主链路**：LLM 超时、报错、没配 key，一律返回上一层的结果。

## 上屏时机

| 模式 | 行为 | 适用 |
|---|---|---|
| `segment`（默认） | 每段定稿后追加，不回退改写 | 绝大多数场景，安全 |
| `live` | 流式 partial 也上屏，退格差分改写 | 最像输入法，但用户中途动光标会出事 |

两种模式都走同一个 `TargetBuffer` —— 它维护「我往那个窗口打了什么」的镜像，
用公共前缀算最小改动。追加时公共前缀就是已写内容，退格数为 0，所以不需要两套代码。

## 本地小模型？

二期再说。Qwen3-1.7B 级别 + llama.cpp 能做第三层，代价是 +2GB 体积、慢 3~5 倍。
现在的架构里换掉 `LlmService` 的实现即可，上层不用动。
